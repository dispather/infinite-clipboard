## 2. 관찰 (결함 판정 아님)

고칠지 여부는 그쪽 원장 소관이고, 우리 쪽에서 이 관찰로 기다리는 회신은 없습니다.

**N1. 가드가 센 «2개» 중 하나는 받을 때 이미 받을 수 없었고, 다른 하나는 로그 없이 목록에서 빠졌습니다.** `[실측]`
가드 때 대기 목록(`transfer_state.json` 의 `receivable`)은 13:11 파일 1개(약 73 MiB)와 13:25 이미지 1개(242 KB)였습니다.
8분 뒤 15:10 에 받기를 요청할 때(앱 «받기» 버튼과 같은 `receive_requests.json` 경로) 목록은 13:11 파일과
**15:09 에 새로 온 파일**이었고, 13:25 이미지는 그 사이 빠져 있었는데 그 일을 적은 로그 줄이 없습니다
(빠지기 직전 15:08:51~15:09:02 에 다른 기기에서 새 offer 4건이 연달아 왔습니다). 받기 결과는:

```
15:10:19,180 WARNING [받기] 실패: offer=efa978f5… reason=superseded retryable=False    ← 13:11 파일
15:10:51,091 INFO    [받기] 완료: 1개 → <다운로드 폴더>                              ← 15:09 파일(79 MB)
```

13:11 파일이 가드 시점(15:02)에 이미 `superseded` 였는지는 모릅니다 `[추정]`. 그랬다면 가드 문구의 «N개가 사라집니다»에
이미 받을 수 없는 항목이 섞여 셀 수 있습니다.

**N2. 업데이트(재시작)할 때마다 클립보드 이력이 비워집니다.** `[실측]` 설치 전 `clipboard_history.json` 4,693 B → 설치 뒤 1,983 B,
항목 1개(재실행 직후 것). `[문서]` 메인 프로세스는 `main.py:192` `self.clipboard_history = []` 로 시작하고,
`_load_clipboard_history_file(` 호출은 `:2938`(이력 «창» 프로세스) 하나뿐이라 메인은 파일을 다시 읽지 않습니다.
그래서 재시작 뒤 첫 새 항목이 생기면 파일이 그 1개로 덮입니다. `history_privacy_mode` 가 켜져 있어 의도일 수 있습니다 `[추정]`.
받기 대기 목록 유실(F1)과 같은 모양이라 적어 둡니다.

**N3. 트레이 이름 두 번 붙는 조건 — 자료 하나 추가.** `[실측 find UIA]` helper 가 띄운 3.0.15 는
`Infinite Clipboard Infinite Clipboard — 서버에 연결됨 — <IP>`(두 번), 오늘 12:44 에 탐색기(`explorer.exe`, 부모 프로세스로 확인)에서
띄운 3.0.14 는 한 번이었습니다. 지난번(재시작으로 뜬 3.0.13 은 한 번, 설치 뒤 직접 띄운 3.0.14 는 두 번)과 합치면
«무엇이 띄웠나»와 관련 있어 보입니다 `[추정]`.

**N4. helper 작업 폴더가 남습니다.** `[실측]` `C:\Temp\ic_update_<무작위>\` 에 `ic-update-helper.ps1`(958 B)만 남고
설치 파일은 지워졌습니다. 업데이트마다 1 KB 폴더가 하나씩 쌓입니다.

## 3. 정리한 것

- 숨김 영역 아이콘은 검증 동안만 작업표시줄에 고정했다가 되돌렸습니다(`unpin` → `restored: true`, 상태 파일 없음). `[실측]`

- 앱은 **3.0.15, 원래 설정 그대로 서버에 연결된 상태**로 둡니다.
- 스크린샷은 이번엔 첨부하지 않습니다 — 알림·진행 창 뒤에 이 PC 의 다른 업무 화면이 찍혀 있어서입니다. 판정은 로그·메뉴 핸들·프로세스 목록으로 했고,
  알림 문구 네 개와 진행 창만 캡처를 눈으로 읽었습니다.
