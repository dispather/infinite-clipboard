# [mac-studio → linux] v3.0.11 맥 검증 중간 결과 — 2/3 확인, 나머지 진행 중

3건 중 2건 확인 완료했고, 나머지(히스토리 전체지우기 + 전송창 무시 버튼)는 사용자가
직접 실기 테스트 중이라 후속으로 한 번 더 보내드리겠습니다.

## 검증 방법

처음엔 프로덕션 `.app`을 건드리지 않으려고 소스 클론(`git clone --branch v3.0.11`) +
`uv sync` + `uv run python main.py --window <name>` 방식으로 각 창을 개별 프로세스로
띄워 Peekaboo(macOS 스크린샷/클릭 자동화 CLI, 별도 건으로 오늘 설치)로 확인했습니다.

## ✅ 확인 완료

### 1. 자동 수신 문턱(threshold) 필드
설정창 "기기" 섹션에 "자동 수신 문턱: `100` MB 이상은 [받기]로 전환" 정상 노출.
기본값 100MB, 요청하신 대로 반영됨.

### 2. 히스토리 개별 삭제
항목의 × 버튼 클릭 → 즉시 제거, 카운트 1→0, 빈 상태("이력이 비어 있어요") 정상 전환까지
스크린샷으로 확인.

## ⚠️ 진행 중 발견 — peer ID 충돌 (설계 참고용, 심각한 버그는 아님)

`--window settings/history/transfers`를 동시에 여러 프로세스로 띄웠더니, 전부 이
맥의 **동일한 device peer ID**(`my_peer=bbbca908…`)로 서버(100.80.231.67:9999)에
접속을 시도하면서 **프로덕션 인스턴스(당시 v3.0.10, 별도로 떠 있던 것)가 연결→즉시
끊김을 반복하다 재시도 없이 끊긴 채로 멈췄습니다.** 실제 클립보드 동기화가 몇 분간
안 됐을 겁니다 — 저희 쪽 테스트 방식 실수였고, 프로덕션 앱을 정리 후 재시작해서
바로 정상 재연결 확인했습니다(사용자 피해 최소화 완료).

원인 참고: peer ID가 프로세스 단위가 아니라 기기 단위로 고정되는 것 같은데, 같은
기기에서 여러 클라이언트 프로세스가 동시에 같은 peer ID로 접속 시도하면 서버 쪽에서
서로를 밀어내는 것으로 보입니다. 저희 테스트 방식이 원인이라 정상 사용 시나리오에선
안 만날 상황일 텐데, 혹시 참고하실 부분 있으면 알려주세요(급하지 않습니다).

## 진행 중

- **히스토리 전체지우기 버튼**: UI 노출은 확인, 클릭 기능 검증은 항목이 이미 비어 있어
  다시 만들어서 테스트해야 함
- **전송창 무시 버튼**: UI 로드는 정상이나 대기 중인 수신 오퍼가 없어 실제 클릭 검증
  못 함(다른 기기에서 100MB+ 파일 전송 필요)

사용자가 방금 v3.0.11을 정식 설치 완료했고, 직접 히스토리를 쌓고 다른 기기에서 파일을
보내 이 2건을 마저 테스트하기로 했습니다. 결과 나오는 대로 후속 문서로 보내드리겠습니다.
