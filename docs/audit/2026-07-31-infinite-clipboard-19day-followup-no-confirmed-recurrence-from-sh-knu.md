# 2. ⚠️ 관찰 — 로그가 "실패"와 "안 붙여넣음"을 구별 못 합니다

`Windows lazy fetch 실패 — 미제공(→fallback)` 이 찍힌 offer를 UUID로 전수 추적해 최종 `파일 조립 완료` 도달 여부를 봤습니다:

```
lazy fetch 실패  32건 → 고유 offer 14개  (UUID 추출 32/32, 미추출 0)
그중 최종 '파일 조립 완료' 도달 =  4개
              도달 로그 없음 = 10개
```

| 날짜 | offer | 최종 조립 |
|---|---|---|
| 07-12 09:37:58 | `0c154e22…` | 없음 |
| 07-12 09:38:12 | `650d63d5…` | 없음 |
| 07-12 09:38:18 | `56777272…` | ✅ |
| 07-12 09:38:26 | `50fe03fc…` | ✅ (실패로그 10회 반복 후) |
| 07-12 09:38:41 | `d36a1ed2…` | 없음 |
| 07-12 09:38:55 | `987b6fa9…` | 없음 |
| 07-13 00:59:07 | `857491a1…` | 없음 |
| 07-13 00:59:17 | `90fa6c3a…` | 없음 |
| 07-13 01:28:34 | `3d3568a1…` | 없음 |
| 07-13 01:28:40 | `6e790807…` | 없음 |
| 07-13 06:39:07 | `d692c811…` | ✅ |
| 07-13 07:20:59 | `49f16d93…` | ✅ |
| 07-23 20:35:55 | `b3bdd44b…` | 없음 |
| 07-23 20:36:08 | `6b578725…` | 없음 |

**"없음" 10개를 실패로 읽으면 안 됩니다.** lazy는 on-demand라서, 사용자가 끝내 붙여넣지 않은 offer도 정확히 같은 흔적을 남깁니다 — `lazy fetch 실패 → fallback` 뒤 아무것도 없음. 두 경우가 로그상 **완전히 동일**합니다.

즉 저는 이 로그만으로 "재발 10건"이라고도, "재발 0건"이라고도 말할 수 없습니다. 사용자 체감 보고와 시각을 맞춰야만 판정이 됩니다. 07-12 회신에서 "로그로 미재현"이라고 쓴 것도 결국 같은 벽이었는데, 그때는 이게 **로그 설계의 한계**라는 걸 몰랐습니다.

## 제안 (선택 — 회신 불요)

offer의 **종료 상태를 한 줄로 남겨주시면** 이 모호성이 사라집니다. 예:

```
[offer 6b578725…] 종료: consumed         (조립 완료)
[offer 6b578725…] 종료: abandoned(ttl)   (아무도 안 가져감 — 정상)
[offer 6b578725…] 종료: failed(<사유>)   (진짜 실패)
```

지금은 성공 경로에만 종료 로그(`파일 조립 완료`)가 있고 나머지 두 경로는 침묵합니다. **침묵이 두 가지 다른 의미를 갖는 구조**라, 다음에 사용자가 "또 실패했다"고 해도 로그로는 여전히 확정 못 합니다.
